# 03 · 性能分析与优化计划

## 测量方法

- 基准脚本：`benchmarks/bench_scanner.py`（阶段 5 新增）。每项基准都用固定随机种子生成合成输入，先预热一次，再运行 5 次取**中位数**；
  峰值内存另外单独跑一次，用 `tracemalloc` 统计（只统计 Python 分配的内存）。
- 热点定位：用 `cProfile` 按 tottime 排序，再针对热点做单项微基准。
- 环境：云端容器（Linux，4 核），Python 3.13.18，基线代码为 `claude/review-fixes` @ `75aba2c`。计时有波动，**只比较相对变化**。

```bash
python benchmarks/bench_scanner.py                  # 全部基准，每项 5 次
python benchmarks/bench_scanner.py cluster --runs 5 # 单项
```

## 基线（5 次中位数）

| 基准 | 输入 | 中位数 | min / max | 峰值内存 |
|---|---|---|---|---|
| `cluster` | `cluster_similar_hashes`，6 万个唯一 pHash（55% 均匀随机、25% 共享高 33 位的「风格」、20% 连拍近邻） | **5887 ms** | 5576 / 6080 | 11.9 MiB |
| `enumerate` | `_enumerate_image_files`，2 万个文件 / 420 个目录（热缓存） | 63 ms | 62 / 84 | 2.5 MiB |
| `exact` | 精确扫描端到端，6000 个文件（热缓存，几乎全部同大小） | **1028 ms** | 996 / 1059 | 3.7 MiB |
| `phash` | 相似扫描端到端，120 张 1600×1200 JPEG | 552 ms | 534 / 564 | 0.4 MiB |
| `thumbnail` | 冷缓存缩略图，60 张 1600×1200 JPEG | 172 ms | 169 / 184 | 0.4 MiB |
| `parallel` | `_iter_parallel_results` 纯调度开销，2 万个空任务 | **743 ms** | 682 / 779 | 1.2 MiB |
| `result_keys` | `main._collect_result_path_keys`，2 万条结果路径 | **165 ms** | 147 / 176 | 4.0 MiB |

补充测量：

- `cluster` 剖析：共访问候选 **2047 万次**，其中约一半的下标 ≤ 锚点、会被直接跳过；实际计算 popcount 985 万次；每个锚点的候选数中位数 746、平均 524、最大 1347。
  耗时分布（cProfile，含剖析开销）：函数体 9.35 s，`_was_cancelled` 2.0 s，`sorted` 1.46 s，`bit_count` 1.36 s，`set.update` 1.2 s。
- 调度开销：同样 2 万个空任务，`_iter_parallel_results` 每项 **37.6 µs**，`executor.map` 每项 9.6 µs。
  热缓存下对 2000 个 70 KB 文件算前缀哈希，**并行 176 µs/文件，串行只要 69 µs/文件**，即调度开销把并行拖得比串行还慢。
- pHash 单张成本（4000×3000 JPEG，单线程）：总计 115.7 ms，其中解码 48.8 ms，`convert('L')` 加 LANCZOS 缩放到 32×32 约 67 ms；
  若用 JPEG `draft('L', (64,64))` 缩小解码，只要 4.6 ms。

## 热点清单

| # | 热点 | 位置 | 当前复杂度 | 耗时 / 内存 | 优化方案 | 预计收益 | 风险 |
|---|---|---|---|---|---|---|---|
| 1 | 相似聚类 | `backend/scanner.py:159-223` `cluster_similar_hashes` | 建索引 O(6K)；查询为 Σᵢ(Cᵢ + Cᵢ log Cᵢ)，Cᵢ 是 6 个桶的并集，其中一半是 ≤ 锚点的无效候选；最坏 O(K²) | 5887 ms @ 6 万；11.9 MiB | 桶内下标本来就是升序，用 `bisect` 直接跳过 ≤ 锚点的部分；不再对整个候选集合排序，只在命中后对少量匹配项排序；`_was_cancelled` 改为绑定 `is_set` 的局部变量调用，减少函数调用开销；保持锚点（非传递）语义、输出顺序和取消行为不变 | 2.5–4× | **低**：纯函数，可以用暴力 O(K²) 锚点聚类做参照、随机对拍 |
| 2 | 结果路径白名单 | `main.py:129-134` `_collect_result_path_keys` | 每条路径一次 `realpath`，每次要 O(深度) 个 `lstat`（本例中每条 4 次）；Windows 上每次 `realpath` 都要打开句柄，开销更大；而且是在 `scan_lock` 内执行的（L1） | 165 ms @ 2 万；4.0 MiB | 按父目录缓存 `realpath(dirname)`，再拼接文件名。H1 修复后，枚举结果里不会再有符号链接文件，所以 `realpath(dir/name) == realpath(dir)/name`；万一遇到链接，回退到逐条 `realpath` | 5–10×（Linux），Windows 上更大；锁持有时间同比缩短 | **低–中**：路径语义，需要补上父目录是符号链接或联接点时的等价性测试 |
| 3 | 并行调度 | `backend/scanner.py:250-294` `_iter_parallel_results` | 每次 `wait(pending, FIRST_COMPLETED)` 都要给全部在途 future（≤ 2W = 16 个）安装或卸载 waiter，总复杂度 O(N·W) | 743 ms / 2 万个空任务（37.6 µs/项）；精确扫描端到端 1028 ms | 改为完成队列：`add_done_callback` → `queue.SimpleQueue`，每完成一项补交一项；保持「在途 ≤ 2W」「取消后不再提交并取消排队任务」「worker 异常记日志并返回空字符串」的语义 | 调度开销 2–3×；热缓存精确扫描 20–40% | **中**：涉及并发；完成顺序本来就不确定，下游都会排序归一化 |
| 4 | pHash 计算 | `backend/scanner.py:86-95` `get_image_phash` | O(像素数)：全尺寸解码 + 灰度转换 + LANCZOS | 12MP：115.7 ms/张；相似扫描基本被它主导 | JPEG 用 `draft()` 缩小解码 | 约 25×/张，是相似扫描最大的杠杆 | **高**：会改变 pHash 数值，从而改变分组结果。需要用真实照片集评估分组差异，并决定是否重调阈值，属于产品决策，**不自动实施** |
| 5 | 删除后清空缩略图缓存 | `main.py:225-226` | 每次删除后，可见缩略图要全部重新生成 | 60 张冷缓存 172 ms | 删除后不再清空：缓存键已经包含 `mtime_ns` 和 size，已删除的路径也无法再通过授权 | 不确定：WebView 文档内的图片缓存可能本来就会复用同一 URL，收益要在真机上测 | 低 |
| 6 | 全量哈希重复读取 64 KiB 前缀 | `backend/scanner.py:442-477` | 大文件候选要多读 64 KiB | 对 3 MB 照片约为 2% 的字节量 | 保存前缀阶段的 `sha256` 状态，从偏移 64 KiB 处继续读 | ≤ 2% | 中（需要在两个阶段之间保存哈希状态） |
| 7 | 文件枚举 | `backend/scanner.py:355-411` | O(条目数) | 63 ms @ 2 万个文件（热缓存）；实际运行时主要受 I/O 限制 | `splitext` 改为 `rpartition` 等微优化 | 很小 | 低 |
| 8 | 前端删除后整表重渲染 | `web/script.js` `removeDeletedPaths` → `renderList` | 每次提交都要 O(组数) 重建 DOM | Node 假 DOM 无法反映真实布局开销，没有测量 | 只重渲染受影响的行 | 结果多时可能明显 | 中（需要改动 DOM 与索引的一致性逻辑） |

## 排序与选择（收益高、风险低优先）

| 排名 | 热点 | 理由 | 阶段 6 分支 |
|---|---|---|---|
| 1 | #1 相似聚类 | 微基准中最大的绝对耗时；纯函数，有暴力参照可以对拍，风险最低 | `claude/perf-cluster` |
| 2 | #2 结果路径白名单 | 改动小，收益明确，还能缩短 `scan_lock` 的持有时间；风险可以用等价性测试覆盖 | `claude/perf-result-keys` |
| 3 | #3 并行调度 | 影响精确和相似两种扫描的所有并行阶段；热缓存下实测比串行还慢；风险中等，但改动局限在一个函数内 | `claude/perf-parallel` |

未入选：#4 收益最大，但会改变产品行为（风险高），作为「建议下一步」交给人工决策；#5 收益不确定；#6、#7 收益太小；#8 无法可靠测量。

## 第二轮：M1–M11 修复后的回归检查

方法：用临时 worktree 检出修复前的 `4db7895`，与 `claude/medium-fixes` 交替运行同一个基准脚本，共 3 轮，每轮每项 5 次取中位数；表中是 3 轮中位数的中位数。
其中 `result_fingerprints` 是本轮新增的基准（`benchmarks/bench_scanner.py`）。

| 基准 | 修复前 `4db7895` | M1 初版（`fstat`） | 最终版 | 结论 |
|---|---|---|---|---|
| `exact` 6000 个文件 | 1064 ms | **1133 ms（+6.5%）** | 1081 ms（+1.6%） | 初版每个文件多一次 `fstat`；8 个线程争 GIL 时，每次系统调用都要释放、再重新获取 GIL。改为多读 1 字节后回到噪声范围 |
| `phash` 120 张 | 605 ms | 609 ms | 同左 | 像素预算没有造成等待（单张约 190 万像素，远低于 1.92 亿的上限） |
| `thumbnail` 60 张 | 202 ms | 211 ms | 同左 | 在噪声内（最小值 176 → 171 ms）；读取 EXIF 方向、预留预算的开销可以忽略 |
| `result_keys` 2 万条 | 63.0 ms | 63.7 ms | 同左 | 改成生成器、与指纹共用之后没有变慢 |
| `result_fingerprints` 2 万条 | — | 90.7 ms | 同左 | M8 新增的开销：比 `result_keys` 多约 27 ms，即每个文件约 1.35 µs 的 `stat`。在扫描线程中、`scan_lock` 之外执行，不会阻塞状态轮询 |

需要注意：Windows 上 `os.stat` 比 Linux 慢得多（要打开句柄），结果很多时，扫描结束阶段可能多出几百毫秒。
如果实测明显，可以改用枚举阶段 `DirEntry.stat()` 拿到的 `(size, mtime_ns)`（在 Windows 上没有额外开销）作为指纹。
代价是指纹的时间点从「扫描结束」提前到「枚举时」，枚举后、扫描结束前被修改的文件会被拒绝删除（更保守）。本轮没有实施，列入建议。

## 第三轮：L1–L13 中与性能有关的改动

- 热点第 5 项「删除后清空缩略图缓存」已随 L8 落实（`b963353`）：删除后不再调用 `clear_thumbnail_cache()`，其余照片的缩略图直接命中缓存。
- 热点第 8 项「删除后整表重渲染」没有做：L8 只让焦点留在原位，整表重渲染保留，改成增量更新风险高于收益。
- L1 让删除时的 `realpath` 不再占用 `scan_lock`；L4 让提前退出时不再空等排队任务。
- 第三轮没有重新运行基准。热路径上唯一的改动是 L4 在 `_iter_parallel_results` 的结果循环外加了一层 `try/finally`，没有单独测量。
